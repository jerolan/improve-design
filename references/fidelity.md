# Fidelity contract

## With mockups

Locate the visual source of truth and the precise screens or states being reviewed. Record the reference, viewport, assets, and proposed deviations. Prefer native inspection of the design file when the tool is available; a screenshot can still be a valid reference.

Reuse the source's tokens, font files or documented font choices, icons, images, labels, and data. If actual components exist, use them. If the prototype must be reconstructed in another tool, treat translation as work that needs visual verification.

Compare rendered output at the same viewport and state. Check page structure, element bounds, line breaks, spacing, type weight, image crops, colors, controls, and state indicators. An overlay or image comparison can help, but font antialiasing differences alone need not block delivery. Fix differences that change the intended appearance or reading order.

A missing asset or unavailable font is a limitation, not permission to silently change the design. Use a reversible substitute when necessary, identify the difference, and avoid claiming exact fidelity. A screenshot used as a backdrop with invisible hotspots is not a complete prototype when the journey requires editable inputs or changing state.

When proposing a visual improvement, update the approved reference or provide an explicit revised mockup before treating the prototype's divergence as intentional. Keep an original reference available for comparison. Do not overwrite unrelated designs or create extra pages and maps merely to document the process.

## Without mockups

Use product context to choose a visual direction suitable for the actual audience and task. Set coherent type, color, spacing, component, imagery, and state choices. Native system typography can be intentional; a custom brand may need supplied or properly sourced fonts. High fidelity does not require ornamental imagery, animation, or external assets.

Build realistic content, hierarchy, controls, and states immediately. A simple form deserves finished labels, spacing, validation, and a credible result. A mockup can be a single polished screen; an interactive prototype needs the whole advertised journey.

Once a direction is accepted, preserve its decisions during feedback. Use a shared set of tokens, components, and sample data so screenshots and interactive states stay aligned. Do not generate a second visual direction accidentally while implementing the prototype.

## Wireframe on request

When requested, use black, white, and gray to review structure, content, and behavior without committing to a visual identity. A wireframe can still be interactive and must complete its advertised journeys. Label it as a wireframe and do not claim high visual fidelity to a colored mockup. Absence of a mockup alone does not mandate this mode.

## Evidence

Save the reference and a representative prototype capture together with their viewport and state. Explain proposed changes and any known differences. For a responsive reference that exists only at one size, distinguish faithful reproduction of that size from inferred layouts at other sizes.

High visual fidelity and a complete journey are separate checks. A prototype must satisfy both when both are requested.
